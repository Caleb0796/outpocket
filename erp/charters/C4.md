## API iron rules — authoritative, MEASURED unless noted

1. `document.modelContext.registerTool(def, {signal})` is the only entry point;
   `navigator.modelContext` removed in Chromium 150. The installed major is
   **152.0.7977.64** (MEASURED); the alias status on 152 is node V0.
2. De-registration only via `AbortController`.
3. `outputSchema` does not exist; annotations are `readOnlyHint` and
   `untrustedContentHint` only. **Assert on exactly these two.** The judging
   client sees **four** things per tool — `name`, `description`, `inputSchema`,
   `annotations` — not three. **Two spellings, one field pair** (MEASURED
   2026-08-29): page JS reads back `readOnlyHint` / `untrustedContentHint`; the
   CDP `WebMCP.toolsAdded` event reports the same two as `readOnly` /
   `untrustedContent`. Pick a channel per assertion and say which; an eval that
   reads the wrong spelling sees `undefined` and reports every tool as not
   read-only.
4. The browser does not validate `inputSchema`. Your negative controls must
   therefore send invalid arguments and assert the *page* rejected them.
5. Revocation does not cancel an in-flight `execute`, and **neither does the CDP
   `WebMCP.cancelInvocation`.** MEASURED 2026-08-29 on the installed **152**:
   cancelling makes `toolResponded` fire with `status:"Canceled"` while the
   page's `execute` **keeps running** — `execute`'s second parameter `opts`
   arrives with zero own keys, so no `AbortSignal` reaches the page and it never
   learns it was cancelled; when it later returns, no further event fires. Use
   `cancelInvocation` so your rig never hangs on a suspended `execute`. **Do not
   write an eval, a log line or a sentence that asserts anything interrupts a
   running call.** Related and also measured: `invokeTool` answers `-32602 "Tool
   not found"` identically for a revoked tool and for one that never existed, so
   no eval may assert the browser distinguishes them.
6. Top-level document only; iframe registrations are never discovered.
7. No binary channel — no eval may deliver an image or PDF through a tool.
8. Budgets: description ≤500 chars, output ≤1500 chars — **PUBLISHED official
   guidance, not enforcement.** E5 measures; it does not enforce, and it does not
   grade them MEASURED.
9. Dynamic surfaces cost ≈1.25× cache write per flip — report this as a cost,
   never as a saving.
10. Graded runs use **`--enable-features=WebMCP`** and that is a **house rule
    about our own configuration**, not a browser constraint. MEASURED 2026-08-28
    by the session owner, Chrome 152.0.7977.64, `--headless=new`, clean dedicated
    `--user-data-dir`, `http://localhost` (`FACTS.md` IR-16):
    **(a) CONFIRMED** — `WebMCPTesting` also exposes the page API *and* the CDP
    `WebMCP` domain; the two flag names are interchangeable.
    **(b) RETRACTED** — the earlier claim that `--headless=new` exposes both with
    no flag is **FALSE**: with no flag, `typeof document.modelContext` is
    `undefined`, headless or headed. It got published because the probe read
    `WebMCP.enable` over CDP, which returns `OK` even where no page API exists.
    **Probe the page API, never a CDP `enable` result.**
    **(c) NEW** — the graded suites therefore **may run headless**; the
    "run headed" instruction is withdrawn along with (b). What you must honour:
    pass the flag, **record `HEADLESS` in every result file**, and carry a
    **no-flag negative control** — that, not headedness, is what proves the flag
    is doing something. This is also what makes **E6** (evals in CI, no display)
    feasible at all.
    The old open gap is closed: `getTools()`/`executeTool()` *are* reachable
    under `WebMCP` with no agent attached. **H2's first hour is now a regression
    gate, and E1 is still gated on it.**
11. `Origin-Agent-Cluster: ?0` silently kills WebMCP — E6 runs against the
    deployed origin, so dump headers before blaming the code.
12. ChatGPT built-in browser: GPT-5.6 Sol/Terra only, Luna disabled, not on
    Enterprise/Edu.

## How a tool is actually invoked — read before you write a suite

The twelve rules above are unchanged in count. This block is new, and it exists
because **the calling convention every earlier revision of this charter implied
does not work.** All of it MEASURED 2026-08-29, headed Chrome 152.0.7977.64,
`--enable-features=WebMCP`, no agent attached. Authority: `FACTS.md` §1.4
(IR-17 / IR-18); harness architecture: `EVAL.md` §2.3.

**From page JS** (this is H3's channel, and the fallback agent's):

- `getTools()` returns a **Promise**, not an array. `getTools().length` is
  `undefined`. Any count assertion is `(await getTools()).length` — written
  without the `await` it compares `undefined` to `undefined` and **passes
  against an empty surface**, which is the exact failure the whole
  no-fake-bridge rule exists to prevent.
- The awaited value is an Array of plain objects with keys `annotations`,
  `description`, `inputSchema`, `name`, `origin`, `title`, `window` — and
  `inputSchema` comes back as a **JSON string**.
- `executeTool('name', args)` **does not work.** It rejects: `TypeError: …
  The provided value is not of type 'RegisteredTool'.` **There is no by-name
  invocation from page JS.**
- The one form that works: `executeTool(descriptor, JSON.stringify(args))`,
  resolving to a **JSON string**. An args *object* rejects with `UnknownError:
  Failed to parse input arguments`; so do `null`, `undefined`, `[]` and a `Map`.
- Both rejections are Promise rejections, not synchronous throws. **A call you
  do not `await` looks like a success and measures nothing.**

**Over CDP** (this is the eval-kit's channel, via `harness/drive.mjs`):

- `WebMCP.enable` first — it is a hard precondition. Without it, or after
  `WebMCP.disable`, `invokeTool` returns `-32000 "WebMCP domain is not
  enabled"` and no events fire.
- `WebMCP.invokeTool {frameId, toolName, input}` — `frameId` from
  `Page.getFrameTree`, `input` an **object** (a JSON string fails
  deserialization: the opposite of the page-JS rule; do not copy one convention
  into the other).
- **The result is `{invocationId}` and nothing else.** The tool's output arrives
  on the matching `WebMCP.toolResponded` event. Correlate by `invocationId`.
- `toolResponded.status` is `Completed` (with `output`), `Error`, or `Canceled`.
  **On `Error`, `errorText` is empty** — the message is in
  `exception.description`. A harness reading `errorText` reports every failure
  as blank.
- Enumerate the surface from `toolsAdded` / `toolsRemoved`, accumulated after
  `enable`. `toolsRemoved` fires one event per tool on `AbortController.abort()`.
- **`Schema.getDomains` does not list `WebMCP`.** That inventory is stale; do not
  feature-detect the domain with it. The reliable discriminator is that an
  unknown method returns `-32601 "'X' wasn't found"` while `WebMCP.enable`
  returns `{}`.
- A page-initiated `executeTool` **also** emits `toolInvoked`/`toolResponded`,
  so the event stream is a complete record of calls from either side — which is
  what "record which layer refused" needs.

**`Runtime.evaluate` keeps two jobs and loses one.** It stays the instrument for
**feature detection** (`typeof document.modelContext…`, V0's `navigator` alias
check) and for **reading page state**. It is no longer the executor, and it
never was one.

**The browser validates nothing on either channel.** `invokeTool` with
`input:{"bad":1}` against a schema with `additionalProperties:false` returned
`status:"Completed"` and the page callback received `{"bad":1}` verbatim
(MEASURED 2026-08-29). Rule 4 holds on both paths: your negative controls test
**our** code.

## Your acceptance bar, per node

Accept predicates are in `erp/graph.json`; L1 copies them verbatim into
`.team/contracts/<node>.txt`. What follows is why, not a second copy.

- **E1 driver skeleton** — and the thing that must not be reinvented:
  `webmcp-eval-kit/src/canon.mjs` is a **PORT of `src/canonical.js` (OCF-1, node
  S11)**, verified against **all seven** vectors in
  `erp/contracts/canonical-vectors.json` as the kit's `npm test`. There was a second,
  independent canonicaliser — `JSON.stringify` over an array sorted by
  `localeCompare`, no kind prefix, nested key order untouched — and it produced
  different bytes for the same surface **always**, which made every "the deployed
  digest equals the frozen digest" assertion unsatisfiable by construction. It is
  deleted. Sort by **codepoint**, recursively; `localeCompare` is ICU-dependent
  and a stranger's clean clone can sort differently. Surface digests are
  `digest('outpocket/surface/1', tools)`. The export envelope is
  `erp/contracts/tool-export.schema.json`'s, with `states` as an **array**. Also:
  `--selftest` must assert a **non-zero tool count** — a byte-identical-twice
  check passes happily against an empty surface.
- **E2 capability suite** — for each of the **six** canonical states (`S0-anon`,
  `S1-emp-home`, `S2-emp-draft-clean`, `S3-emp-draft-dirty`, `S4-emp-submitted`,
  `S5-aud`), the expected tool-name set is asserted exactly. **Set equality, never
  count equality**, and that is not pedantry: `S4-emp-submitted` and `S5-aud` both
  carry 6 tools and differ by exactly one name, so a count assertion passes even
  when the auditor is handed the employee's surface.
- **E3 negative controls** — every must-fail case declares **`pairsWith`,
  `provingNode` and `brokenBy`**. The runner builds the pairing map from
  `pairsWith` and **fails the run if any state in `evals/surfaces.expected.json`
  has an empty pair set**; the old predicate was `count(mustFail) >= count(states)`,
  i.e. `14 >= 7`, trivially true, and it permitted the actual situation in which
  two states had no dedicated must-fail case at all. **N-15
  `neg-commit-without-human` is mandatory**: a synthesised client-side sign
  response POSTed to commit must return 409 `E_NOT_SIGNED`. It is red today and
  goes green only when S5/S12 land the server-owned decision state — which is what
  a genuine negative control looks like. Relabel as **guards**, in a separate
  table, anything that cannot fail in a reachable state; "every row reads refused"
  means nothing if some rows could never say otherwise.
- **E5 surface accounting** — deterministic, **provably** zero model calls. The
  proof is a denied syscall, not an environment variable:
  `node --import webmcp-eval-kit/test/no-net.mjs …`, where `no-net.mjs` throws
  from `net.Socket.prototype.connect` and `dns.lookup`. MEASURED: Node's global
  `fetch` (undici) **ignores `HTTPS_PROXY`** without an explicit `ProxyAgent`, so
  the old proxy-based predicate would have exited 0 on a run that called
  `api.openai.com`. Record which denial mechanism ran in `accounting.json`'s
  header, since "zero model calls" is a published claim. Two runs, byte-identical.
  **Reference points, with their grades attached:** the raw character counts are
  MEASURED — signed-out 1 tool 395, employee 5 tools 1,947, clean draft 13 tools
  6,682, auditor 6 tools 2,070. The token figures (~99 / ~487 / ~1,671 / ~518) are
  exactly `ceil(bytes/4)`, i.e. **OUR-ESTIMATE from a formula, not tokenizer
  output**; citing them to a judge as measured token counts would be circular.
  A difference of a couple of characters per state between the raw count and the
  post-`canon()` wire bytes is **the canonical form, not a harness bug** — three
  incompatible "bytes per state" definitions were in circulation for the same
  state (395, 397, 280), and exactly **one** may appear in the README. A large
  divergence is your harness; suspect it then.
- **E6 CI** — runs against the **deployed commit, not the working tree**. The
  workflow's first step asserts `curl -s $URL/version` equals `git rev-parse HEAD`
  and fails the job otherwise, and fails if the response carries
  `Origin-Agent-Cluster: ?0` (only `?0` is fatal; `?1` is harmless). A green run
  is proven mechanically before D5 —
  `gh run list --workflow eval.yml --json conclusion -q '.[0].conclusion'` equals
  `success` — not by a human looking at the Actions tab.
- **E7 results table** — the row count equals the suite count in
  `evals/latest.json` and every number in the table matches the JSON. The
  published Bytes column is `canon()` wire bytes; the export's `accounting` block
  is an internal cross-check and is labelled as such wherever it is shown, never
  mixed into the same column.
- **E10 mutation check** — `--verify-controls` applies each case's declared
  one-line `brokenBy` mutation, re-runs the case, and **fails the run if the case
  does not flip** from refused to permitted. This is the only mechanical
  definition of "a real negative control", and it is the thing that makes your own
  charter bar below enforceable rather than aspirational. Five controls were
  verified as passing vacuously against the current tree; this is what catches the
  sixth.

## Banned behaviours

- Grading against the working tree when the contract says deployed.
- An eval that calls a model. E5 is deterministic and model-free by definition —
  and proven so by a denied syscall, never by `HTTPS_PROXY`.
- A second canonicaliser, or `localeCompare` in any sort that feeds a digest.
- A `grep -c … returns 0` check: `grep -c` printing `0` **exits 1**, so in an
  `&&` chain it always fails. Use `! grep -q`.
- Reporting a bare `PASSED: n/m`. That framing is the pass-rate framing this
  charter bans two lines down; publish the per-case ledger.
- Touching `evals/blind/**`, `tests/redteam/`, or C3's report.
- Writing `evals/results.json`, `outpocket/tools.export.json`, `bin/eval.mjs`
  bare, or `eval/run.mjs`.
- Loosening an assertion to make a suite green. A failing eval is your correct
  output.
- Shipping a negative control with no `brokenBy`, or one that cannot fail in any
  reachable state. **These tests must be red when the mechanism is removed** — an
  eval suite with no failing negative control proves nothing, E10 is what proves
  it mechanically, and you state that in your README.
- Publishing a pass rate without publishing what the negative controls were.
- Editing README outside the `<!-- EVAL:BEGIN -->` / `<!-- EVAL:END -->` markers.
- Any claim retracted in HANDOVER §5, and specifically the claim that a
  stable/dynamic tool surface saves prompt-cache tokens.
