## Your acceptance bar, node by node

Accept predicates are in `graph.json`; L1 copies them verbatim into
`.team/contracts/<node>.txt`. What follows is why, not a second copy.

- **S11 — the canonicaliser. Numbered last in the lane, scheduled FIRST in it.**
  OCF-1 and the seven-vector suite: object keys sorted **recursively by
  codepoint** (never `localeCompare`, which is ICU-dependent and can sort
  differently in a stranger's clean clone), NFC strings, integers only, and
  `digest(kind, value) = sha256(kind + "\n" + canon(value))`. It carries the
  carve-out permitting `$`-prefixed keys (`$schema`, `$ref`, `$defs`) inside an
  `inputSchema` subtree, plus the numeric carve-out for JSON Schema keywords —
  without both, a real tool definition is not canonicalisable at all.
  **This is the only canonicaliser in the project.** The eval kit's
  `webmcp-eval-kit/src/canon.mjs` is a *port* of it, verified against the same
  seven vectors. There was a second, incompatible definition; it produced
  different bytes for the same surface always, which made every "the deployed
  digest equals the frozen digest" assertion unsatisfiable by construction. It is
  deleted. Vectors v6 and v7 (the provenance flip) are the standing regression
  case; keep them.
- **S1** Single-file Node server with cookie sessions, and **exactly two
  personas: `chen` (employee) and `ruiz` (auditor)**, matching the frozen enum in
  `erp/contracts/eval-case.schema.json`. There is no third persona; it had no name, no
  role and no credential, and it is deleted. Deployment target is **Render paid
  0.5c-512mb ($7/mo)** — the only landing that needs no code change. The free tier
  sleeps at 15 minutes and its 750 h/month against a 744-hour month means a
  keep-warm ping fills the quota and suspends every free service in the workspace.
  **D1 must deploy exactly ONE instance, and the deploy notes must say why:** S6's
  TOCTOU closure is true by construction of a single-process server with
  synchronous state mutation inside each handler, and a second instance
  reintroduces the race with no test in this repo that would catch it.
- **S2** Per-request role authorization. **The legacy pattern
  `countinghouse/src/erp.js:101` is a client telling itself 403 — that is not a
  boundary.** `tests/acceptance/curl-403.sh` proves an auditor session gets a real
  HTTP 403 from the server on **every** route in the exported write-route table,
  and the script fails if the table has a route it does not cover. No silent gaps.
  This file is a deliverable, not a convenience.
- **S3 — 3.0 hours, and it is not a port.** `countinghouse/src/policy.js:28` is
  `export const FX = { USD: 1, EUR: 1.09, GBP: 1.28, CNY: 0.14, JPY: 0.0067 }` —
  **floats, which cannot enter a canonical form two implementations agree on.**
  Amounts stay **integer cents**; FX rates become **integer micro-units (rate ×
  1e6)**; every digest downstream is re-derived. The served policy document must
  contain **no decimal number anywhere**. And the rule count is **19, not 16**:
  15 line-level codes plus 4 report-level codes, `R01`–`R19`, re-counted from
  source and matching the frozen policy schema. Version `2026-08.1`. The version
  must be observable to the page so F5 can display it. **The old 1.0 h estimate
  and the old predicate would not have detected whether the migration happened at
  all.** S3 is on the critical path.
- **S4** Deterministic violation envelope `{code, severity, field, fix,
  candidates}` on **every** write tool, conforming to the frozen schema. Same
  input, same envelope, always.
- **S5 — the human sign gate, and the server owns the decision.** This is the
  single most serious defect the audit found, and it was a working forgery. The
  old `sign_response` was **entirely client-authored**: every field was a
  constant, attacker-chosen, or copied verbatim out of the `sign_request` the
  server had just returned. Walking the whole rejection table, a synthesised
  response passed every code and committed — writing a chain entry attesting a
  human signature, by a client-chosen name, at a client-chosen time. The tamper
  defence worked *because nothing changed between sign request and commit*; the
  forgery succeeded for exactly the same reason. A digest comparison cannot
  distinguish "human signed and nothing changed" from "nobody signed and nothing
  changed". Build it this way, and only this way:
  - Sign requests carry **server-held state**: `open → answered(signed|declined)
    → committed | expired`. Commit requires `answered`.
  - The click POSTs `/api/sign/{request_id}/respond`. The server records
    `decision` from the body but takes **`signed_by` from the session cookie and
    `at` from the server clock — never from the payload.**
  - **Delete the `signature` object from `commit_request`.** Reduce it to
    `request_id`; the server looks up its own record.
  - Add **`E_NOT_SIGNED` (409)** to the rejection codes.
  - Add **`request_id` to the snapshot projection**, so a digest can never be
    presented against a different sign request.
  - The negative control **N-15 `neg-commit-without-human`** is the proof: a
    synthesised client-side sign response POSTed to commit returns 409
    `E_NOT_SIGNED`, and the stored `signed_by`/`at` are unaffected by anything in
    the request body. It fails today and passes only once this lands.

  > ### What this node is allowed to claim, and it is less than it sounds — R-13
  >
  > **A second forgery survives everything above, and it is open today.** The
  > attacker never renders the dialog: it POSTs `/api/sign/{id}/respond` itself,
  > with the page session cookie, echoing back the `snapshot_digest` and
  > `revision` the server issued one call earlier, and then commits. **All eleven
  > rejection codes were walked and none of them fires.** This is inside our own
  > **N-04** threat model — curl, session cookie, no browser — so it is not an
  > exotic attack and you do not get to scope it out.
  >
  > **The only sentence you may write, in a comment, a commit message, the README
  > or a demo line, is: "a commit cannot be made without a POST from the
  > authenticated session to `/api/sign/{id}/respond`."** Anything stronger is
  > struck on sight — *not* "a commit cannot be made without a human decision",
  > *not* "Layer 0 answers did a human decide", and **no `forgeryClosed` flag in
  > any schema you touch**.
  >
  > **State what R-1 bought together with what it cost, because they are the same
  > change.** The attacker loses the ability to choose the name and the timestamp
  > — both now come from the session and the server clock. So the record it
  > produces is a **true attribution of a false event**: signed `chen`, at a
  > genuine server time, **forensically indistinguishable from a real click** in
  > the day book forever. That is arguably a worse forensic outcome than the
  > forgery it replaced, and writing it down is part of the node.
  >
  > **The `confirm_token` is defence in depth, not a proof — build it as such.**
  > Mint it with the sign request; deliver it **only into the rendered dialog's
  > DOM**; **never** return it in a tool-call result and **never** in any
  > `/api/sign/{id}` response body; require it on `/respond`, rejecting with
  > **403 `E_NO_CONFIRM_TOKEN`**. It raises the cost of the attack. **It does not
  > establish personhood.** Its whole value is a function of **open unknown
  > `V3`**: if an agent-initiated fetch carries the page session cookie *and* the
  > agent can read the DOM, the token is reachable and the vector reopens for that
  > caller. `V3` got **more** load-bearing under R-1, not less.
  >
  > **N-16 `neg-respond-without-click`** is scripted verbatim as the attack above
  > and **records the honest outcome in both directions**, failing if it changes
  > silently either way: with no token required the commit **succeeds** (HTTP 200,
  > a chain entry) and the case is `KNOWN-OPEN`; with the token required, a caller
  > that cannot read the DOM gets 403 and the case is `REFUSED`. **A negative
  > control that asserts the outcome you wish you had is not a control.** The
  > +0.5 h on this node (3.5 → 4.0) is the token, N-16 and
  > `tests/signature.test.mjs`.

  - **Write both suspension modes behind one switch from the start**:
    suspend-until-signed, and the two-call `{status:"awaiting_signature", ticket}`
    handshake. I1's **V4** measures how long a suspended execute survives in the
    built-in browser; if that is shorter than a human needs to read a dialog, you
    flip the switch. This is a Day-1 design constraint, not a Day-4 rewrite, and
    it is recorded in `graph.json.contingencies`.
- **S12** Report revision counter and **atomic sign lock**. While a sign request
  is open, every mutating endpoint returns **423** with a code field; the revision
  counter increments on every accepted mutation and is carried in the sign
  request; and the lock is taken in the **same synchronous step** as the snapshot
  computation, proven by a test that interleaves two requests and shows no window
  between them. (This node was published elsewhere under the id `S10`, colliding
  with L1's contract freeze. It is **S12**.)
- **S6** Server-side re-canonicalisation and reject on mismatch. **This is the
  TOCTOU closure and it is the only part of the sign gate that is actually ours**
  — the sign-gate concept itself is publicly claimed by `webmcpui`, and OpenAI's
  client already applies its own confirmation policy for consequential actions.
  Our difference is mechanism: digest binding plus server-side re-canonicalisation
  before persistence, using **`src/canonical.js`, the same implementation the
  client used**, never a second definition. Canonicalise deliberately against key
  order, whitespace, unicode normalisation, numeric formatting and duplicate keys
  — C3 will attack all five. State the claim with its precondition attached:
  **given a single server instance**, graded OUR-ESTIMATE, true by construction.
  It is not a proven property of a horizontally scaled deployment.
- **S7** SHA-256 hash chain over the day book. **The digest must cover the
  `source` field**, or provenance is forgeable by rewriting attribution. The test
  flips one byte of a `source` field and asserts verification fails at that index.
- **S8** Per-field provenance: `{value, source:'agent'|'human', ts, actor}`.
  A human edit after an agent write flips `source` and appends two day-book
  entries with distinct sources. **Do not present the 0-of-420 keyword count as
  evidence that nobody else does this** — generic audit/ledger hit 53%, so the
  gap is "unrewarded", not "unclaimed", and keyword-derived emptiness is exactly
  the mistake this project has made three times.
- **S9** Deterministic reseed on boot. The judging window **2026-09-04 10:00 →
  2026-09-21 17:00 PT is unattended**; a restart must be equivalent to a clean
  initial state. Boot twice, diff `/api/state-digest`, expect identical.

## Iron rules that reach your lane

There is **no binary channel** — an agent cannot deliver an image or PDF, so the
receipt path is human-upload only and the agent may only link an existing id.
Enforce that server-side, not just in the tool surface, and say **page-enforced**,
never browser-enforced. The browser does **not** validate `inputSchema`, so
**every endpoint validates its own input in code**; assume the client is hostile.
Revocation does not cancel an in-flight `execute` (Chrome 153+, and the installed
major is 152) — your sign gate's copy and behaviour must both reflect that.
`Origin-Agent-Cluster: ?0` in a response header silently kills WebMCP: never set
it, and check the deployed headers with I4 at D1 — **only `?0` is fatal**; `?1` is
the opposite setting and is harmless.

## Banned behaviours

- Client-side authorization presented as a boundary.
- Floats anywhere in money or FX. Integer cents, integer micro-USD rates, and no
  decimal number in the served policy document.
- Saying "16 rules". It is **19**, `R01`–`R19`.
- A second canonicaliser, or `localeCompare` anywhere in a sort that feeds a
  digest.
- Accepting a client-authored signature object, a client-supplied `signed_by`, or
  a client-supplied `at`. The server owns the human decision; it does not verify a
  claim about one.
- A violation envelope that varies between identical inputs.
- Persisting a signed record without re-canonicalising and comparing.
- A hash chain whose digest omits `source`.
- Accepting an agent-supplied binary or base64 attachment through any route.
- Typing `policy/`, `tests/curl/`, `erp/contracts/violations.schema.json` (plural),
  or `erp/contracts/FREEZE` without the `.md`.
- Starting lane X before the submission is in — and it is C2's lane regardless.
- Any claim retracted in HANDOVER §5 — in particular "we invented deterministic
  policy contracts" (Oracle's `expenseErrors` and UCP's envelope precede us) and
  "original material never resides in the system" (it does; attachments are
  uploaded **and stored** — the honest narrowing is that derivation context is not
  persisted).
