# Pit — V3

Reported by **I1** under D-31, in its own words, transcribed by L1.

**TRIED.** V3 was open not because nobody had measured it but because **everything had been
measured on the wrong subject**: `evidence/V3.json` said `same-session` on the V5 probe over
`http://localhost:8795`, and `V6-consent-gate.json` supplied a remote re-run still on the probe
origin. My charter binds the closing measurement to **S1**, which landed with a working session.
I wrote `harness/v3-cookie.mjs` and a fixture at `harness/fixtures/v3/index.html`, served by
`server/index.mjs` **imported, never reimplemented**, through the `pageRoot` parameter D-50 added
for exactly this — so V3 gets a page on S1's origin without waiting on F1 and without touching
`src/page/`, which is not mine. **The fixture holds EXACTLY ONE fetch**: the tool's execute calls
it and the driver's page-side arm calls the same closure, so the arms differ in **who initiated**
and not in a `credentials:` spelling that drifted between two copies. Arm B ran remote, per the
charter rule that a green localhost run is not evidence.

**HAPPENED.** Green, exit 0, `same-session`, stable across five runs; A1's two bodies
byte-identical. Two findings the accept did not ask for.

**First — THE ACCEPT CAN PASS ON AN EMPTY INPUT, and A2 is the proof.** With no session both arms
return `401 {"error":"E_NO_SESSION"}` and are therefore byte-**equal**, so a run that discovered
nothing satisfies "the bodies are equal" exactly as well as A1 does. **Equality alone is not the
finding; A1 ∧ A2 ∧ A3 is.** That sentence is in the evidence at
`accept.canThisAcceptPassOnAnEmptyInput` rather than left to be noticed.

**Second — arm B's raw body equality is FALSE and it is not a cookie finding.** The probe's
`/whoami` stamps a per-request `at` timestamp, so two calls 90 ms apart differ no matter what the
cookie did: **raw-body equality is structurally unsatisfiable on the endpoint the accept names.**
Both bodies recorded unaltered beside a timestamp-stripped comparison (true) and a note that **the
instrument failed there, not the browser.**

Incidental: `document.cookie` is `""` in all three S1 arms while the cookie is present and being
sent — which is why no JS-side check could have answered this, and a curl-based one would have
proved only that Node can attach a header.

**CHANGED.** Nothing in `erp/graph.json` or `erp/PATHS.md`, in either direction; nothing outside
my declared outputs — ownership 3/3, 0 violations. I re-ran the Layer-0 lint **pointed explicitly
at my three files**, so its exit 0 is not a vacuous pass on an empty set. The prior localhost
reading was **preserved, not overwritten** — carried verbatim under `priorReading` with its
Chromium-151 / built-in-browser provenance intact — and the carry-forward is **idempotent**
(verified: a second run does not nest the script's own output).

**EARLIER.** Two design errors caught. *Before running:* I had navigated to `origin + '/'`, but S1
maps `/` to a filename that is **not stable** — `/index.html` in my base, `/page/index.html` after
D-66, which was already sitting in the main checkout. **The arm would have 404'd the day that
merged, for a reason with nothing to do with V3**; naming `/index.html` explicitly resolves
identically under both. *Before shipping:* the first draft put only the `/api/me` pair in the
accept block, so a strict reader would have found the accept's literally named endpoint missing
from the block meant to answer it — both pairs are in there now. I also nearly let the run imply
"the agent has the session"; the narrow negative claim and what would falsify it are now in
`instrument.whatIsAndIsNotBeingClaimed`.

**GRADE.** MEASURED for cookie carriage on the real server under plain Chrome 152 over CDP. **NOT
measured, explicitly still open** (2 `openItems`, not closed early): the built-in browser against
the real server, and the consent gate against the real server. D-19 still has TWO preconditions
and this measures ONE. No claim about which agent acted.
