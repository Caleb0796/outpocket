no hits. The harder collision: `kb/webmcp/RETRACTED.txt` is **not** on the charter's four-entry

**EARLIER.** Gate 1 was rejected on the first submission: `node tools/lint-layer0.mjs` (clause 1,
repo-wide sweep, no path on the command line) exited 1, tripped by three files, not one —
`tests/fixtures/banned-sample.js` (the planted violations, correctly present), and two files this
node itself authored that quote the same banned/retracted strings in order to document or test
the ban: `tools/lint-layer0.mjs`'s own source (the BW-14 selftest fixtures at the bottom of the
file, and the doc comments describing the ban) and this pit, `kb/pits/G4.md` (the GRADE section
below narrates the retracted strings in prose). The reviewer named the resolving shape precisely:
clause 1 (sweep, exit 0) and clause 2 (fixture named explicitly, exit 1) are the same file only
for the fixture, and the fix is a swept-vs-named distinction, not a change to the fixture or to
the predicate's four-entry EXCLUDE array. I added `SWEEP_EXCLUDE`, a third list distinct from
both `EXCLUDE` (the predicate's literal array) and `REGISTER_FILES` (the RETRACTED.txt
mechanism) — naming this file's own source and the fixture path — applied only in `main()`'s
argument-less default-sweep branch, filtering `gitLsFiles()` before `runScan()` ever sees these
paths. It does not touch `isExcluded()`, `isRegisterFile()`, or `runScan()` itself, so an explicit
invocation — `node tools/lint-layer0.mjs tests/fixtures/banned-sample.js`, or hypothetically
against this pit — still scans and still fails the moment the path is named on the command line;
only the argument-less sweep skips them.

A second round put `kb/pits/**` itself onto `SWEEP_EXCLUDE`, generalizing the fix from a literal
list to two named classes — and that second move was wrong, and reverted. The correct class,
kept: a verbatim extract of an already-excluded file (`.team/contracts/**`, whose ACCEPT field is
generated byte-for-byte from `erp/graph.json` by `tools/contract.mjs`, and `erp/**` is already on
EXCLUDE — scanning it is scanning the excluded source wearing a different path). The wrong class,
removed: treating a pit as the same kind of thing as `kb/webmcp/RETRACTED.txt`'s REGISTER_FILES
case. It is not. A registry file's whole job is to hold the retracted strings so
`--assert-register` can find them — nothing is lost by skipping the WORD/RC pass over it, because
its content is checked by a different mechanism entirely. A pit has no such second mechanism:
it is authored prose, and nothing else in this project reads it — no test, no schema, no review
step checks a pit's claims against the ruling record. Excluding `kb/pits/**` from the sweep would
have meant a retracted claim asserted (not quoted-to-ban) inside a pit could ship undetected,
with no other instrument positioned to catch it. This was demonstrated concretely: an assertion
of the RC-2 write-count claim, planted inside a pit, under the `kb/pits/**` exclusion, produced
zero hits from a repo-wide sweep. That is a hole in the one file class most likely to carry a
retracted claim as a live assertion rather than a historical quote.

The rule this pit — and every pit after it — now follows instead of an exclusion: **a pit names
the ruling and states the correct claim; it does not quote the retracted string verbatim.**
"R-20 puts the write count at seven, computed from `annotations.readOnlyHint !== true`" cites the
ruling and asserts the corrected fact without reproducing any of the five banned/retracted
strings. Applied to this pit's own history above: the two duplicate-role rows are named by their
`BW-NN`/`RC-NN` ids rather than by quoting their text, and the BW-14 worked example is described
by its grammatical shape (plural-noun vs. singular-possessive) rather than by quoting either
form. Nothing about the underlying content changed — the same rows, the same worked example, the
same reasoning — only the citation form. `--selftest` now carries a ninth check that plants a
retracted-claim assertion at a `kb/pits/` path and proves it is both NOT sweep-excluded and
caught by `scanFile()`, so this exclusion cannot be quietly reintroduced without that check
failing.

I did not take the alternative route the reviewer also offered on the first rejection (rewriting
the linter to load its BW/RC literals from a registry file the way `kb/webmcp/BANNED.txt` already
does, so its own source never carries the strings at all) — the BW-14 selftest specifically needs
the exact phrase text inline to exercise the `\b`-anchoring boundary against both the banned form
and the innocent plural, and moving that into an external registry would add an indirection with
no clause it newly satisfies, since `SWEEP_EXCLUDE`'s narrower, single-class form already makes
clause 1 pass without weakening the instrument, deleting a planted string, or touching the
fixture. I did not weaken any pattern, did not delete any planted string in the fixture, and did
not soften the fixture's content — the eleven violations it trips are unchanged.
