# Pit — H6

*Reported by I1 in its own words at the merge gate (D-74/D-31); L1 transcribed, did not compose.*

**TRIED.** Started from the predicate rather than the feature, because it is the weakest one I
have had: **"5 of 5 under 120 seconds with per-step timings" is satisfied perfectly by a rig
that starts and stops.** So I wrote the grader first and the runner second. The rule I built
from is the one H4 taught me — ask what the check would have printed had it failed — and I
applied it **to the pass counter itself before anything else, because that is the component
whose failure mode is invisible.** Reused `harness/dump-state.mjs` as the single observer
rather than writing a second one, which was not just tidiness: it means H4's `E_EMPTY_DUMP` and
`E_DEMO_INCOMPLETE` guards protect every rehearsal run without my re-deriving them, and **a
future weakening of either is caught in two nodes at once.**

**HAPPENED.** Green first time, 5/5, **and I did not believe it** — 0.6 seconds per run
including a Chrome launch looked impossible, and **"impossibly fast green" is the exact shape
of a rig that did nothing.** So I timed a single `drive.mjs` invocation independently: 0.614s
real, exit 0, RP-1018 filed with 3 lines. Headless Chrome against localhost really is that
fast, and the number was honest. **The interesting part is that the verification run FAILED** —
exit 1, no filing — because my throwaway server script hard-coded a path to the I1-H4
worktree, whose `index.html` predates the mount tag. That was my rig being wrong, not the
product, and it accidentally re-confirmed the unmounted-page failure path works. Then
`--break-run` gave 4/5 with run 3 named, and `--selftest` gave all eight clauses failing on
demand.

**CHANGED.** `harness/rehearse.mjs` and `evidence/rehearsal.json` new. `harness/drive.mjs` grew
one stderr timing line. `src/page/demo-mode.js` got per-step ms and the disclosure fix — H4's
file, merged, mine, and **I flagged the cross-node edit rather than widening quietly**, same as
with the banner on H3. Nothing in `erp/graph.json` or `erp/PATHS.md`. `--out` added for exactly
one caller **so a deliberately-broken run cannot poison the evidence file.**

**EARLIER.** **THE TIMING CHANNEL DECISION WAS THE WHOLE NODE AND I ALMOST GOT IT BACKWARDS.**
My first instinct was to put per-step ms into the dump, where the state is — it is the obvious
place, the dump is the observation, everything else about the run lives there. **That would
have broken H4's accept immediately and silently-ish:** two runs at the same seed would differ
by a millisecond, `diff` would exit 1, and the failure would have looked like
non-determinism in the demo rather than what it was. I caught it **while writing the comment
explaining where timings go, which is the second time in two nodes that WRITING DOWN WHY has
caught something reading the code did not.** The generalisable version: **A DERIVED MEASUREMENT
AND THE THING IT MEASURES MUST NOT SHARE A CHANNEL WHEN ONE OF THEM IS GRADED FOR
BYTE-STABILITY.** Durations, hashes of durations, anything wall-clock — they belong beside the
artifact, never inside it. I had already written that rule for INSTANTS in `dump-state.mjs` and
did not generalise it to my own new field one node later.

**GRADE.** MEASURED. 5/5 through `accept-gate --run-clean 0`; 4/5 with run 3 named under
`--break-run`; 8/8 grading clauses shown failing under `--selftest`; wall time cross-checked
against an independent single invocation; both banner configurations read off the rendered DOM.
NOT measured: the built-in browser, the deployed origin, and **any claim to flake resistance —
five runs of a seeded demo measure that the machine is not on fire and that the same seed
replays, which is worth having and is not robustness.** That limit is in the evidence file's
header rather than in this report only, so a later reader cannot infer more than we established.
