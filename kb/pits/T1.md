The RED: the first real run of the accept predicate reported three `registerTool` call sites
reachable from a worker entry, and all three were inside `tools/check-toplevel.mjs`'s own
`--selftest` fixtures. The checker flagged itself. Cause, found by reading which lines it
picked: the string-blanker did not understand regex literals, and this file is full of
patterns like `/<iframe\b[^>]*\bsrc\s*=\s*["']([^"']+)["']/gi`. The scanner saw the double
quote INSIDE the pattern, entered string mode, and desynchronised for the whole remainder of
the file, after which fixture strings read as live code. Fixed properly — `blank()` now
tokenises regex literals, using the previous significant token to tell a regex from a
division — and the desync is now a `--selftest` case (`regexy.js`) so it cannot come back.
Nine selftest checks, nine pass.

Two measurements worth carrying, neither of which is a request to change anything. First,
**span 1 of this node's predicate exits 0 vacuously when `src/page` does not exist.** I
measured this before writing a line of the checker: `find src/page …` prints its error and
exits 1, but the pipeline's status is `xargs`'s, and BSD `xargs` on this machine does not
invoke the utility at all on empty input (`printf '' | xargs -0 /bin/echo X` prints nothing
and exits 0). So the gate was already green this morning, over a directory that did not
exist and a checker that did not exist. The node's own notes record the *globstar* form of
this defect; this is a second face of it that survived the fix, and it is platform-dependent
— GNU `xargs` would invoke the utility once with no arguments. I did not touch the
predicate. What I did instead is the part that is mine: the checker prints its own coverage
(argv count, files scanned, entries, call sites) and **exits 1 rather than 0 when it scanned
no JavaScript at all**, so on the platform where it is reached, a vacuum reports as a vacuum.
Second, `js/mjs scanned 25 / html scanned 1` was checked against an independent `find` of the
tree and matches exactly, so the scan is whole rather than truncated.

**EARLIER.** I had written the regex-literal desync into the checker's own header as a "known
imprecision", with a soothing sentence about how it affects only where a scan resumes and not
whether a finding is real. That was wrong on the facts — it produced three false findings on
the very first real run — and wrong as a habit. **A caveat in a header comment is a bug you
have decided not to fix, dressed as documentation, and writing it down makes it less likely
to be fixed rather than more**, because the next reader treats it as a known limit rather
than an open defect. The tell was available before the run and I ignored it: I knew the
blanker did not handle regex literals, and I knew the file I was writing was unusually dense
in regex literals containing quote characters. Second, smaller, and a direct cousin of the
L0 trap: I read `LINT_EXIT=0` off `node tools/lint-layer0.mjs 2>&1 | tail -25` and briefly
believed the G4 lint was clean. That 0 was `tail`'s. The real exit is 1, on two pre-existing
files (`.team/contracts/G4.txt`, `kb/pits/S10.md`, both last written at `e3044d8`, neither
mine, and it is not this node's gate). L0's finding was that a seat's environment is part of
its test; the same is true of a seat's *shell plumbing*, and `$?` after a pipeline is the
last stage's, not the interesting stage's. Both of my accept runs went through
`tools/accept-gate.mjs --run-clean`, which is exactly why neither of them was ambiguous.
