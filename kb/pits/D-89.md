## I3 — the channel

**TRIED.** Read F7's `sign-install.js` in full before writing anything, then built the
server-side channel and the page-side companion. Merged `origin/main` before committing
rather than rebasing an old tree, **so the suite number reflects what is actually there now
rather than a stale count from before F7/F5/V4 landed.**

**HAPPENED.** `GET /api/sign/{request_id}/confirm-token` — session-scoped, promoting
`peekConfirmTokenForDialog` from test-only to the real production channel — **and it is NOT,
and must never become, a registered WebMCP tool, which is the entire property.**
`openForDialog(openBody, signal)` is a NEW, clearly separated companion;
`beginSign()`/`continueSign()` are left **byte-for-byte unchanged**, so R-13/R-44's narrow
`{status, ticket}` tool-facing contract still holds. Test 2/2, suite 192/192 at the time,
FREEZE clean.

**THE ROOT CAUSE IT FOUND.** `sign-install.js:173` reads `awaiting.confirm_token` and `:164`
reads `awaiting.request_id` from `beginSign()`'s return — **and `beginSign()` deliberately
never carries either.** So `mountSignDialog()` always received `confirmToken:""` and
`request_id:null`, and **a real click posted to `/api/sign/null/respond`.** I3 read F7's file
in full and then ruled it **not F7's fault**: F7 wired the seam to a field `beginSign()` was
never going to supply. Two correctly-scoped modules and a seam nobody owned — the fourth
instance of that class, **arriving one layer inside the fix for the third.**

**CHANGED.** `server/sign.mjs`, `server/index.mjs`, `src/page/sign-bridge.js`, plus the test
and DEV-016. Hit the ownership hook twice and **did not bypass it** — left both files
untracked and handed them over, the way S5 handled DEV-E3.

**GRADE.** Green.

## UX — the wiring

**TRIED.** Confirmed the defect before fixing it: all three fields undefined, every time.

**HAPPENED.** 9/9 with I3's branch, **5/9 without it** — and the four failures are a
DELIBERATE TypeError, loud, not a degradation. **No fallback:** a bridge lacking
`openForDialog` is REFUSED AT CONSTRUCTION with a message naming the reason, because the
kind version — falling back to `beginSign` for older bridges — **would silently restore the
exact path this repairs.**

**CHANGED.** The call moved into the PROVIDER rather than the port, because the provider owns
the transport and needs `openForDialog`'s ticket for `continueSign` anyway. The port now
passes **the server's own `sign_request` straight through** instead of reassembling one —
which matters beyond the null: **the digest the human is shown and the digest the POST
acknowledges must be the SAME value the server issued**, and rebuilding it locally is how
those drift apart without anything erroring.

**EARLIER, and it is the generalisation.** **browserDialogPort HAD NO TEST.** Every test in F7
stubs the dialog port — that is what made the node testable and what made its clause 2
meaningful — **and it is exactly why the DEFAULT port, the only one that ever runs in the
page, was never executed by anything.** The rule: **EVERY INJECTION POINT SPLITS THE CODE
INTO A TESTED HALF AND A SHIPPED HALF, AND THE SHIPPED HALF IS INVISIBLE TO EXACTLY THE
TESTS THE INJECTION MADE POSSIBLE.** A default implementation of an injectable seam needs its
own test, always, and that is not the same thing as a test of the seam.

And a second, about a habit that looks like care: **DEFENSIVE DEFAULTS ON A REQUIRED VALUE
CONVERT A LOUD FAILURE INTO A WRONG ONE.** `?? null` and `?? ""` are why this failed silently
rather than throwing. Had it read `awaiting.request_id` bare, the URL would have said
`/api/sign/undefined/respond` on the first manual click and someone would have found it in
minutes. **A default is right for something optional and wrong for something essential**, and
it was applied without distinguishing.

**GRADE.** Green as a pair.

refusal with a reason rather than a hang, which is the right end for it; the
orphaned-open-record window is I3's to know about.
