# Pit — T6

**TRIED.** Took L0's two lessons as preconditions rather than as reading. Before editing
anything I ran the accept predicate through `node tools/accept-gate.mjs T6 --run-clean 0`,
which lifts span `[0]` verbatim out of `erp/graph.json` and strips `FORCE_COLOR`, and
recorded the baseline: 9 tests, 8 pass, 1 fail, **exit 1**, the failing subtest named
`auditor surface: read-only by construction`. Establishing the RED first meant that when it
later went green I was comparing two runs of the same command in the same declared
environment, not a memory of one against a run of the other. Then R-9 option (B): read
`src/erp.js` to find the honest way to build a side-effect-free reader, patch the two
declared outputs by unique-anchor string substitution (the script refuses on an anchor that
matches zero or two places, so a silent mispatch cannot happen), re-run the same span, and
finally measure all six canonical states directly rather than inferring them from the tests.

**HAPPENED.** Green: the span exits 0 at 9/9, the named subtest reads `ok 3`, and the whole
suite is 24/24 — the same 24 L0's gate (7) counted, now with zero failures instead of one.
The load-bearing discovery was in `src/erp.js`: it does **not** export `getReport`; the
closure keeps it private and only `openReportOrNull` reaches it. `src/erp.js` is not one of
this node's declared outputs, so `get_report` reads through the two things that *are*
exported — `erp.state.reports` and `erp.verdict(id)` — and I checked the purity of that path
by hand rather than assuming it: `verdict` → `validateReport`, with `priorHashUseFor` and
`receiptById` as pure lookups. None of the three writes, logs, or emits. That matters,
because the tool's entire justification is that it is side-effect-free, and a `verdict()`
that quietly logged would have made the new tool exactly as dishonest as the one it
replaces. Measured after the change: distinct tools **15 → 16**; `get_report`'s description
307 chars against the 500 budget (PUBLISHED guidance, not enforcement); annotations confined
to the permitted two; no `outputSchema`. The six canonical states measure
`S0-anon 1 · S1-emp-home 5 · S2-emp-draft-clean 13 · S3-emp-draft-dirty 12 ·
S4-emp-submitted 6 · S5-aud 6`, i.e. the state table is unchanged in shape — `get_report`
lands **only** on the auditor surface, where it displaces `open_expense_report`.

**CHANGED.** `src/tools.js` and `tests/surface.test.mjs`, and nothing else in the tree.
Nothing in `erp/graph.json` or `erp/PATHS.md`, in either direction — not to explain the RED,
not to reach the green. Beyond the set swap I strengthened the named test itself: it now
snapshots `openReportId` and `dayBook.length`, dispatches every tool on the auditor surface,
and asserts both are unmoved. That is inside the node, not beyond it — the test is named
"read-only **by construction**", and a version that only checks `annotations.readOnlyHint`
is precisely the hint-we-ask-a-model-to-believe that R-9 (B) exists to abolish; it would
pass again the moment someone re-added `open_expense_report` with a hint pinned on it. Two
throwaway patch/verify scripts were written and deleted before the commit; `git status` at
commit time shows exactly the two declared outputs.

**EARLIER.** Two near-misses, both caught before they reached the file. First, reuse: the
obvious body for `get_report` was `reportStatusLine(erp)`, which is already written, already
formats a header, and reads the **open** report — so on an auditor surface where nothing is
open it would have described the wrong report, or none, while the id argument was silently
ignored. The tool that must not touch `openReportId` is exactly the tool that must not read
it either, and the helper that looked like reuse was the one helper that encodes the
assumption being removed. Second, symmetry: `get_report` reads like it belongs next to
`get_open_report` on every surface, and adding it to the employee `base` would have been a
one-word change that broke 5/12/13/6 in four places. Both were caught by measuring the six
states rather than trusting that the test file's counts covered them. One thing I should
flag rather than fix: my own charter's T5 rationale says `S4-emp-submitted` and `S5-aud`
"both carry 6 tools and differ by exactly one name". That was true *before* this node; after
it they differ by two each way (`create_expense_report`, `open_expense_report` against
`get_report`, `get_day_book`). The argument it supports — set equality over count equality —
is strengthened, not weakened, and nothing in `erp/graph.json` is affected, so this is a
note for whoever writes T5, not a ticket. Operationally: under worktree isolation this
harness refuses Bash heredocs as "too complex to verify", so file authoring has to go
through the Write tool; worth knowing before losing two calls to it.
