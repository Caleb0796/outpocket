# Pit — L0

**TRIED.** Worked L0's seven gates in order, running each predicate verbatim out of
`erp/graph.json` rather than retyping it. Built `tools/l0-gate.mjs`, which extracts the
backtick-delimited commands from `L0.accept` and executes them with `sh -c`, so the string
that runs is provably the string in the authority. Same discipline for the two other things
this node copies: `erp/DECISIONS.md`'s D-17 row is lifted out of `erp/RUNBOOK.md` §2 by
`tools/l0-decisions.mjs`, and `package.json`'s `scripts` block was verified by `grep -cF`
against the literal span in the accept text.

**HAPPENED.** All seven gates green; `main` is at `a1f650b` and the remote sha was verified
equal to local HEAD. One gate cost most of the night. Gate (4) exited 1, and the run banner
really did arrive carrying SGR codes — `ESC[1mreasoning effort:ESC[0m low`, confirmed by
`cat -v`, by `od -c`, and by `spawnSync` with piped stdio. I concluded that codex-cli
0.144.6 colours unconditionally, that the predicate was therefore unsatisfiable, and I filed
a deviation ticket asking PM to amend gate (4) and to re-grade a MEASURED claim in
`erp/FACTS.md` §14. **That conclusion was wrong and both requests were withdrawn.** The
cause was `FORCE_COLOR=3`, exported by the resident session L1 itself runs inside; it
forces colour even into a pipe, and it is also why `NO_COLOR=1` did not help. Same
invocation with `FORCE_COLOR` removed prints a clean `reasoning effort: low` and the gate
exits 0. The profiles were correct throughout — base config is `ultra` and all four banners
moved to low/medium/high/high, which also confirms §14's flat-key layout.

**CHANGED.** Nothing in `erp/graph.json`, in either direction — not while the gate read RED,
not to make it green. `tools/l0-gate.mjs` grew a `--run-clean` mode that strips
`FORCE_COLOR` from the child environment and changes nothing else, and prints which
environment it used so the two runs can never be confused. The ticket was corrected in
place rather than deleted: raised, root cause wrong, closed by the raising seat, no
amendment requested.

**EARLIER.** An unexplained `exit 1` got a *theory* before it got an *environment check*.
The observation was sound; the generalisation — "the codes are unconditional, therefore the
predicate is broken" — skipped one question: what in **this** shell is producing them. The
tell was in hand and I misread it: `NO_COLOR=1` failing to suppress colour is evidence that
something is *forcing* colour, not evidence that colour is unconditional. `env | grep -i
color` would have closed it in ten seconds, before a ticket existed. The deeper habit worth
keeping: when a predicate greps another program's human-readable output, the environment is
part of the test, and a seat's own harness is the least visible part of it. **Two seats got
opposite results from the same command on the same machine** — that is the finding, and it
is not in any document yet.

**Carry this to every seat, because it is not a gate-(4) detail.** Every resident seat runs
with `FORCE_COLOR=3` exported by its harness, so **any** accept predicate that pipes a
colourising tool's output into `grep` fails the same way, silently and with no diagnostic.
A sweep of `erp/graph.json` finds five pipe-to-`grep` predicates, in `L0`, `V5`, `D1` and
`D2`. Four grep `curl` headers or HTML and are safe, because neither colourises. The one at
risk was `L0`'s, because `codex` is the only one of them that writes for a terminal. The
next seat to add a predicate that greps a CLI's human-readable output should run it through
`tools/accept-gate.mjs --run-clean`, and should not spend an hour concluding the tool is
broken. `--run-clean` prints which environment it used, precisely so a green run and a red
run can never be confused for each other.

Second, smaller: the first RED report was written as though the graph were at fault. The
discipline held — nothing was relaxed, and gates (6) and (7) were held rather than pushed
past — but the ticket's *tone* asserted a defect in the authority on one seat's evidence,
and asking to re-grade a correct MEASURED claim is a heavier act than raising a blocked
gate. Escalate the blockage; do not escalate a verdict about the authority until the
environment has been ruled out. **The peer review session `mcp-6d` challenged the RED and
was right about the conclusion** (gate green, withdraw the re-grade) **and wrong about the
mechanism** (it proposed a transient from profile files being written concurrently with the
run; it was not that — the failure reproduced deterministically before and after all four
existed). **Not I1.** I1's only involvement in gate (4) was being warned not to build on the
SGR claim; an earlier revision of this pit credited I1 with the catch and saddled it with
`mcp-6d`'s wrong mechanism, and both halves were wrong. Being challenged is what produced
the correct answer, and neither session had it alone.

**Confirming an observation three ways is not the same as testing the explanation once.**
My three confirmations — `cat -v`, `od -c`, `spawnSync` — all inherited the same
contaminated environment, so they re-confirmed the observation and never touched the
inference drawn from it. `mcp-6d`'s single confirmation was a timing correlation it never
tested. Same error, opposite directions.
