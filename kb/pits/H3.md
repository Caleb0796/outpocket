and read the merged tree before writing anything — which is what turned this from a build
into a fit. `drive.mjs --fallback` already existed (built under D-61) and its own header had
already worked out the design: `src/page/fallback-agent.js` "installs the page's own
getTools/executeTool when WebMCP is disabled". So the shape was settled and the job was to
find the seams. They were all there and all named: `globalThis.outpocketTools` (T2's
registry), `globalThis.outpocketShell.refreshEnvBanner({simulated})`, and a reserved empty
`#agent-banner` whose neighbouring comment in `index.html` said it must never be overwritten
because H3's label is "the more important message when both apply". Somebody had thought
about this carefully before me. The module installs a `document.modelContext` shim EAGERLY
and resolves the registry LAZILY, because the three module tags evaluate in an order
`index.html` owns and not us; it never shadows a real API; and it reproduces the real API's
REFUSALS from `erp/FACTS.md` IR-18 — Promise from `getTools`, TypeError on a by-name
`executeTool`, TypeError on one argument, args must be a JSON string — because a lenient
shim would let this page pass a run it could never pass under real WebMCP, which is the same
defect class as a gate that cannot fail. `happy.json` I wrote to be READ: `drive.mjs` now
cross-checks every `walk[].count` against MEMBERSHIP in the frozen contract, because a
scenario file whose only job is to exist is a check that discovered nothing and those
numbers have to be able to be wrong.

**EARLIER.** You asked the right question, so here is the uncomfortable answer: **an hour
before, I had literally typed "the honesty condition, which is an acceptance condition" into
that module's header — and then verified only the accept.** What I would tell myself is
narrower and more useful than "check more things": **WHEN YOU INSTALL AN OBJECT THAT
SATISFIES A DETECTOR, GO AND RE-READ EVERY READER OF THAT DETECTOR.** My shim satisfies
`typeof document.modelContext !== "undefined"`, and that exact predicate is how at least
three places in this repo decide what to TELL A HUMAN. I knew that predicate better than
almost anyone here — I defended it in H5 against the `navigator` alias reading and pinned it
in both directions — and I still did not ask what installing a convincing fake would do to
the code that trusts it. The generalisable rule is: **adding a new object to a shared
namespace is an edit to every reader of that namespace, and the readers are findable in about
ninety seconds.** And I should be honest that I did not find this by discipline. I found it
because I refused to infer the never-shadow guard from a green `--assert-flips` run and went
to read `installResult` out of the live page; the lie was sitting in the same JSON blob, two
fields down. The catch was a by-product of one good habit, not of looking in the right place.
The habit is the part worth keeping: **a green assertion tells you what the code DID, never
what the page SAYS.**

**GRADE.** MEASURED. The walk 7/7 on the mounted page at both ends of the tag-placement
range, the real-WebMCP path unaffected, and the guard's own answer read out of the live page
rather than inferred — flag on gives `installed:false` "a real API is never shadowed"
`real:true`, flag off gives `installed:true` `simulated:true`. Banner before and after read
off the rendered DOM, not from the source. NOT measured, and worth saying since this node is
the demo's survival path: nothing here was run in the ChatGPT built-in browser, and no claim
is made anywhere about attesting WHICH agent acted — this module is the proof that we cannot,
because at the tool boundary it is indistinguishable from a third-party one.
